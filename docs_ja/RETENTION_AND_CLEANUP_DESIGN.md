# 保持と掃除の運用補助：設計記録

2026-11-06 に作成した当初の設計を残しています。以下の記述は設計時点の案です。
その後の実装、現在の API・コマンド、確認結果は [保持量の観測とコピーの掃除](RETENTION_AND_CLEANUP.md) を参照してください。

## 採用する範囲

最初の実装は、保持状況の観測と、利用終了を排他で確認できたコピーの掃除に限定します。
実行中 DLL の自動アンロードは追加しません。

| 目的 | 方法 |
| --- | --- |
| 更新を重ねた際の保持量を把握する | ホスト内のロード記録と、コピー領域のファイル量を別々に表示 |
| 再起動すべきか判断する | 既存のロード試行予算、保持中のネイティブ参照数、コピー量を表示 |
| 終了後のコピーを片付ける | セッションを一意に識別し、生存中ずっと保持するファイルロックで除外 |
| 掃除の失敗からやり直す | 削除専用領域へ移してから削除し、部分失敗を報告して再試行 |

今回の読み取りでは、現在の一時領域 `flow-reloader/<PID>/` に57ディレクトリ、407ファイル、
81,668,096 bytes（約77.9 MiB）がありました。数値は2026-11-06の一時点のファイル長の合計です。
プロセスの生存、DLL のロード状態、実メモリ使用量、物理ディスクの占有量を測定した値ではありません。
ファイル削除は行っていません。

## 現状から分かること

- `GenerationBudget::used()` は共有 budget ごとの累積ロード試行数。静的 API、失敗・破棄候補も含み、
  DLL 数でもメモリ量でもありません。既定32枠は維持し、掃除によって枠を返しません。
- RequestRouter と旧 FlowRunner は共通の `GenerationOwner`／`copy_library` を使います。
  開けた候補は、その後の ABI・契約検証に失敗しても既定で KeepLoaded となります。
- 現在の `RETIRED` は退役したネイティブ参照の待機リストです。
  現用・準備中の DLL は含まれないので、その件数だけでは保持総数を数えられません。
- `LibraryCopy::drop` は削除を試みますが、削除エラーは観測できません。
  KeepLoaded の退役リストも、プロセス終了時のコピー掃除を保証しません。
- 現在のコピー先は PID 単位です。PID の存在確認やファイルの古さだけを、削除許可に使わない設計にします。

根拠となる実装は [世代保持](../flow_reload/src/runner/generation.rs)、
[コピー作成・削除](../flow_reload/src/runner.rs)、[予算](../flow_reload/src/routing/limits.rs) です。
DLL を閉じるための既存条件は [アンロードの契約](UNLOAD_SAFETY.md) を維持します。

## 観測する値

### ホスト内のスナップショット

`retention_snapshot()` を仮の入口とし、ホスト内の当該 SDK 実体が把握するネイティブ画像を集計します。
全 Router・旧 FlowRunner・失敗候補を対象にし、別に組み込まれた SDK 実体や他プロセスまで合算しません。

| 値 | 定義・限界 |
| --- | --- |
| `tracked_native_images` | SDK が生存させているネイティブライブラリ参照数。OS の物理的なモジュール数ではない |
| `recorded_copy_bytes` | それらのコピー作成完了時のファイル長の合計。実メモリ量でも現在の実ファイル検査でもない |
| 現用／準備中／退役と検証結果 | 採用、検証拒否、候補破棄を区別。拒否された画像も保持量に含める |
| `KeepLoaded`／`WhenIdle` | 保持方針。WhenIdle でも、この表示から自動回収はしない |
| コピー削除の失敗 | 対象 ID・パス・I/O エラー。元のロードエラーを上書きしない |

各画像にはロード試行ごとの `ArtifactId` を付けます。Router の世代番号とは別にします。
同じ基準世代から複数候補を prepare できるため、世代番号だけでは画像を区別できません。
静的 `from_api`／`prepare_api` は予算を使いますが、ネイティブ画像数・コピー量には含めません。

Router の `generation`／`in_flight`／受付状態、budget の `used`／`limit` は既存 API から併記します。
`in_flight == 0` や Arc の参照数を、アンロード許可として表示しません。
Future と Waker が保持する参照の完全な内訳も、最初の版では推定しません。

記録は画像の作成・採用・退役・解放時に更新します。観測のために新しい画像参照を保持せず、
スナップショットは所有する値だけを返します。SDK の Router／Future の Send 性は変えません。
内部ロック中に DLL の関数、ロガー等の利用者コールバック、ファイル走査を呼びません。
解放済みの詳細履歴を無制限に保存せず、必要な累積件数だけ残します。

### コピー領域の検査

別の `inspect_cache` が、ファイル数・ファイル長の合計・セッション状態・読めない項目を報告します。
走査は明示操作にし、フレームやリクエストの poll ごとには実行しません。
走査上限を設け、途中で打ち切った場合は部分集計と明示します。生存中のセッションはコピー作成と競合し得ます。

外部コマンドは他プロセスの保持画像数・メモリ量を取得しません。
ディスク上のコピー数と、ホスト内スナップショットを混同しない表示にします。
RSS／private bytes の自動取得や DLL ごとの実メモリ帰属は最初の版に含めません。

## コピーの管理単位

新しいコピーだけを、既存の一時ルート配下の別形式へ移します。

```text
<temp>/flow-reloader/
  <PID>/...                         # 旧形式。表示のみ
  managed-v1/
    namespace.lock                 # 名前空間の操作を直列化。削除しない
    sessions/
      <SessionId>/
        session.meta               # 固定 magic、形式版、SessionId、PID、作成日時
        lease.lock                 # このセッションを利用するホストが保持
        copies/<ArtifactId>.<ext>   # SDK のコピーだけ
    trash/
      <SessionId>/...               # 利用終了を確認し、削除専用に移したセッション
```

SessionId は PID だけにせず、プロセス／SDK 実体ごとに新規作成し、再利用しません。
名前の候補が衝突しても、ディレクトリの新規作成が失敗したら別名で再試行します。
ArtifactId もセッション内で一意にし、コピー先を新規作成して上書きを防ぎます。
日時は表示・任意の保存期間フィルターにだけ使い、一意性や生存確認の根拠にはしません。

session.meta は小さな版付き固定形式とし、読み取りサイズと各項目長を制限します。
削除先の絶対パスや任意の子パスは記載しません。コピー先は管理領域と ID から構成します。
プロジェクトのソース、`target/`、Cargo キャッシュ、DB サンプルのデータは対象外です。

### 生存中のロック

最初のネイティブコピー作成前にセッションを初期化します。
`namespace.lock` を取得してからディレクトリ・lease・meta を作り、lease の排他ロックを取ってから公開します。
初期化途中で失敗・終了して完全な meta が残らないものは、不明な領域として自動削除しません。

lease のハンドルは Router の Drop、最後のワーカーの終了、prepare の失敗で閉じません。
ホストの SDK 実体がプロセス終了まで保持し、明示 unlock は公開しません。
SDK 自体を途中でアンロードする埋め込み方は最初の契約に含めません。
子プロセスへこのハンドルを継承・複製しないことも確認します。意図せず保持された場合は掃除を見送る側に倒します。

ロックには標準の `File::try_lock` を第一候補とします。Rust 1.89 以降にあり、
ロック競合を待たずに判別できるため、このためだけの依存追加は不要と考えられます。
ロックの扱いとハンドルの寿命は [Rust の File 契約](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock) に従います。
実際の Windows／Linux での相互排他・プロセス終了時の動作は、実装時に別プロセスで検証します。
ロック非対応・権限不足・未知の I/O エラーは「終了済み」に読み替えません。

## 掃除の手順

掃除の既定動作は候補一覧の表示です。削除は明示的な apply でだけ行います。
確認済み一覧を後からそのまま信用せず、apply 時に再走査・再検査します。

1. 管理ルートと形式を検査し、`namespace.lock` を非ブロッキングで取得する。
2. 対象 SessionId・meta・構造を再検査する。自プロセスのセッションは常に除外する。
3. 既存 lease を新規作成・切り詰めせず開き、排他ロックを試みる。
   競合なら InUse、エラーや欠落なら Unknown として削除しない。
4. ロックを取得できても、未知のファイル、形式不一致、リンク、再解析ポイントがあれば見送る。
5. namespace の排他を保持したまま清掃側の lease を閉じ、`sessions/<id>` を `trash/<id>` へ移す。
   移動先が既にあれば上書きしない。SDK は trash からロードせず、既存セッションを再使用しない。
6. trash 内を再検査し、既知の通常ファイルを個別に削除する。空になったディレクトリだけを削除する。
7. 削除済み件数・ファイル長、スキップ理由、失敗を返す。一部失敗は成功全件として報告しない。

最初の版では掃除終了まで namespace の排他を保持し、複数の掃除を直列化します。
新規セッション作成が競合した場合は CacheBusy を返し、無期限には待ちません。
既存セッションでの通常ロード・実行は namespace ロックを必要としません。
掃除はフレーム中の自動処理にせず、必要なら件数上限で小分けに実行します。

移動前に中断された場合は元のセッションを再検査します。
移動後の trash はロード対象に復帰させず、次の apply が同じ namespace 排他の下で削除を再試行します。
部分削除後も meta は最後まで残し、最終段階で残った空の trash ディレクトリには `remove_dir` だけを使います。
meta の破損・不明ファイルがある場合は、勝手に補完せず見送ります。

### 削除の前提と境界

対象は、同じプロトコルを守るホストが使う、同一利用者の管理下にあるローカルの専用領域です。
ホストと掃除コマンドは同じルート解決を使い、意図した絶対パス内にあることを検査します。
symlink／junction 等を経由して外部へ到達する対象は扱いません。パスの正規化だけでは競合対策にならないため、
名前空間の排他と、操作直前の構造検査を組み合わせます。
非協調的な同一利用者による同時書き換え、攻撃者の管理するルート、ネットワーク FS は対象外です。
必要な私有性やロック動作を確認できない環境では削除を無効にします。

このロックは、SDK のコピー利用と掃除の排他です。任意の別プログラムが DLL を直接ロードしたことまで検出しません。
コピーを他プロセスのロード元に渡さず、元のビルド成果物を渡す契約とします。
実装には無条件の `remove_dir_all` や広い glob 削除を使いません。

旧形式の `<PID>/` にはこのプロトコルがないため、最初の版では容量とパスの表示だけにします。
既存の407ファイルを、この設計だけで安全に自動削除できるようになるわけではありません。
旧ホストの終了を確認した上での手動整理は引き続き別扱いとします。

## API とコマンドの想定

公開名・型の細部は実装時に確定します。スナップショットと掃除を分け、アンロード API は呼びません。

```text
retention_snapshot()      ホスト内の記録を値として取得
inspect_cache(options)   ファイル量と候補・スキップ理由を取得
clean_cache(options)     再検査して適格なセッションだけ掃除し、結果を返す
```

CLI は `flow_reload` パッケージの小さなホスト側 bin を想定します。以下は未実装の使用例です。

```text
cargo run -p flow_reload --bin flow-cache -- inspect
cargo run -p flow_reload --bin flow-cache -- clean
cargo run -p flow_reload --bin flow-cache -- clean --apply
```

`inspect` と apply のない `clean` は削除しません。表示のために欠けた管理ファイルを作成しません。
InUse、Unknown、Legacy、I/O エラー、部分集計を区別し、削除ゼロの理由が分かる出力にします。
旧形式や不明対象を強制削除するオプションは付けません。
削除前のファイル長は物理的な空き容量の増加と同一視しません。

## 実装順と完了条件

| 段階 | 変更する場所 | 完了条件 |
| --- | --- | --- |
| 1. 観測 | 共通のコピー／GenerationOwner と新しい診断モジュール | 現用・準備中・拒否・破棄・退役を数え、静的 API と予算を区別。観測が寿命を延ばさない |
| 2. 管理コピー | 共通の copy_library とセッション管理 | Router／旧 Runner の両方を新形式へ。プロセス寿命の lease、途中失敗、ID 衝突を検査 |
| 3. 掃除 | ホスト側ライブラリ関数と小さな CLI | 既定は表示、apply で再検査、trash 再試行、旧形式・不明対象の除外 |
| 4. サンプル・CI | テスト、開発手順、必要な診断表示 | Windows と Linux の別プロセス試験を通し、残課題の実装・検証済み範囲を更新 |

必要な検証は次のとおりです。

- 同じ世代からの複数 prepare、ABI／契約拒否、候補 Drop、ロード自体の失敗を集計する。
- Future／Waker、登録処理の終了待ち、Router Drop 後も保持量を過小に数えない。
- 静的 API は画像ゼロ、予算は消費。コピー掃除でも budget は変化しない。
- 生存中のホスト、Router 全破棄後も生存するホスト、停止・強制終了したホストを別プロセスで比較する。
- 同じ PID を meta に持つ別 SessionId、初期化途中、壊れた meta、lease 欠落、ロック失敗を扱う。
- 二つの掃除、新規セッション作成との競合、dry-run 後の状態変化、trash 移動／削除途中の中断を扱う。
- 未知ファイル・リンク・再解析ポイント・ルート外パスを削除せず、適格なコピーだけが消えることを確認する。
- ファイル削除失敗・容量走査の打ち切りを明示し、再試行できる状態を残す。

ファイルロックと実 DLL はネイティブ試験で確認します。純粋な分類・集計は通常のテストで検証します。
この設計段階では新規の実行時テスト結果や、掃除の安全性を実証した結果はありません。

## 今回含めないこと

自動アンロード、TLS／デストラクタの終了検出、管理外処理の強制停止、
メモリ上限の保証、掃除によるロード予算の再利用、自動再起動、GUI 専用画面、
任意ディレクトリや他ユーザーの掃除は含めません。
WhenIdle を拡張する場合は、この補助機能とは別に終了・帰還の証明と実 DLL 検証を設計します。
